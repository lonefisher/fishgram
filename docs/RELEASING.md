# FishGram protected candidate and signing gate

This workflow prepares internal candidates and a fail-closed signing request. It does not make a public release, tag, upload, or index change. The root `fishgram.json` remains `autoUpdate: false` and `releaseReady: false`; only the explicit protected product-candidate build enables the updater.

## Protected product candidate

`product-candidate.yml` is manually dispatched from protected `main`, with the configured protected `candidate` environment. It checks out the exact dispatch commit and recursive pins, requires a clean tracked and untracked workspace, and verifies that the reviewed FishGram public trust bundle is present and root-signed before exposing `FISHGRAM_API_ID` and `FISHGRAM_API_HASH`. The secrets belong only to that protected environment. PR workflows do not receive these secrets.

The workflow restores only the existing exact Windows dependency cache (`Libraries` and `ThirdParty`) or prepares those dependencies. It then builds Telegram, Updater, and Packer with product identity and production FishGram update trust, packages only recorded payload bytes, exports corresponding source once from committed Git objects, and binds its external `candidate-record.json` after both archives exist. The retained internal artifact contains the candidate ZIP, embedded build manifest, Packer, corresponding-source ZIP, and external candidate record. Raw build logs, CMake/API cache, and credentials are excluded.

The current checkout has no `config/update-trust` production public bundle. The workflow must fail before reading API credentials until the reviewed FishGram root public key, issuer public key, root-signed manifest, and detached signature are committed at that path. Test fixtures and private keys are never accepted there.

## Signing preparation

After a human has tested the exact downloaded artifact on clean Windows 11, completed all eight restricted-search acceptance cases and the full updater workflow matrix, and recorded the cloud conclusion for those same archive, source archive, and program hashes, generate the QA template from `candidate/candidate-record.json` and commit the completed file under `release/qa/`. The external `candidate-record.json` is the sole signing record: it binds the candidate ZIP and corresponding-source ZIP (`name`, `size`, and SHA256), program hashes, parent/source/recursive pins, and reviewed tools. Do not submit the package's embedded `build-manifest.json` as the signing record; it cannot authorize signing by itself. Every required QA check and the exact `sourceArchive` binding are mandatory.

Dispatch `sign-release-candidate.yml` from protected `main`, supplying the successful candidate run ID and QA basename. Before candidate artifact download, the workflow queries GitHub API and requires the same repository, `.github/workflows/product-candidate.yml`, `workflow_dispatch`, successful conclusion, `main` branch, matching head SHA, successful `candidate`/`candidateapproved` job, and uniquely run-owned artifact. It then verifies external candidate record, candidate ZIP, bound source ZIP and its Git blob contents, QA, reviewed pins, and Packer hash before exposing issuer secrets. No build or recompilation occurs.

The configured protected `release` environment supplies the encrypted PKCS#8 issuer PEM and passphrase as step-scoped secrets; `ISSUER_KEY_ID` is a public environment variable. If production trust files or this issuer ID are absent, signing stops; a maintainer must install the reviewed public trust bundle and environment variable through protected repository configuration. Test trust is never a fallback. Python consumes and removes both secret environment entries only after the independent preflight and Packer signing-input checks, applies a temporary restrictive ACL, and removes the encrypted key file after signing. OpenSSL receives the password through stdin (`-passin stdin`) and the signing payload through a temporary public-data file; neither is passed on the command line. The tool matches the decrypted key's actual Ed25519 public key to the reviewed production issuer PEM and root-signed manifest, checks expiry/revocation/channel groups, and rejects a single issuer when any required AND group cannot be met. Packer embeds the detached signature. Python parses the result, confirms payload and unsigned fields are unchanged, verifies the Ed25519 signature and root-signed trust manifest, then writes only the signed package and a public signing record. No root private key is used.

Local signing uses the same gate and Packer flow with `--private-key` pointing to an encrypted issuer PKCS#8 PEM; its password is read with `getpass`. The command never accepts a passphrase argument or a plaintext private key. A public signing record and successful local signature do not publish a GitHub release, tag, attachment, index, or trust key.

Neither workflow creates a GitHub release, tag, public attachment, or channel index. Public release and first-install acceptance remain blocked until real Windows 11 and workflow QA, production signing, signed-package verification, and recovery acceptance are complete.

`key-maintenance.yml` checks committed issuer metadata daily and creates a deduplicated maintenance issue when expiry is within 45 days. It requires a real production trust bundle and explicit maintenance enablement, which are not configured yet. Issue writes use the repository-scoped workflow token. Recovery tools and the native cross-baseline snapshot hook have local synthetic tests; real account recovery and first-public-release acceptance remain incomplete. The separate [publishing workflow](PUBLISHING.md) consumes these reviewed signed artifacts and verifies public downloads before promoting the channel index.
