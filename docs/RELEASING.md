# FishGram protected candidate and signing gate

This workflow prepares internal candidates and a fail-closed signing request. It does not make a public release, tag, upload, or index change. The root `fishgram.json` remains `autoUpdate: false` and `releaseReady: false`; only the explicit protected product-candidate build enables the updater.

## Internal signing before installation acceptance

An update package must exist before its installation and recovery can be tested. A reviewed schema 2 QA document may therefore use `kind: fishgram-signing-qa` to request an internal signed candidate. It still binds the exact cloud ZIP, source, programs, and commits; `sameCandidateCloudConclusion`, `localWindows11`, `hashVerification`, and `noAccountData` must be true. `searchEightAcceptance` and `updaterFullMatrix` remain their actual boolean results. The protected release environment still requires human approval.

This request is accepted only by the signing path. The publisher requires `kind: fishgram-candidate-qa` with all checks true, or the explicitly approved first-Beta policy in [BETA-RELEASE.md](BETA-RELEASE.md) with all remaining search and updater checks passed. After testing the signed package, complete the same committed QA file for the same candidate. The signing record retains the original request bytes and hash; the publication gate checks that only the request kind, approval time, and completed checks changed. The signed package is reused rather than rebuilt or signed again.

## Protected product candidate

`product-candidate.yml` is manually dispatched from protected `main`, with the configured protected `candidate` environment. It checks out the exact dispatch commit and recursive pins, requires a clean tracked and untracked workspace, and verifies that the reviewed FishGram public trust bundle is present and root-signed before exposing `FISHGRAM_API_ID` and `FISHGRAM_API_HASH`. The secrets belong only to that protected environment. PR workflows do not receive these secrets.

The workflow restores only the existing exact Windows dependency cache (`Libraries` and `ThirdParty`) or prepares those dependencies. It then builds Telegram, Updater, and Packer with product identity and production FishGram update trust, packages only recorded payload bytes, exports corresponding source once from committed Git objects, and binds its external `candidate-record.json` after both archives exist. The retained internal artifact contains the candidate ZIP, embedded build manifest, Packer, corresponding-source ZIP, and external candidate record. Raw build logs, CMake/API cache, and credentials are excluded.

The product workflow uses `release_gate.py package-candidate`; `package-telegram.ps1` is an internal development helper. Product packaging rejects test identity, disposable trust, mismatched recipe flags or changed program bytes before creating output. Payload files, Packer, and their build-directory ancestors must be ordinary paths inside the checkout; symbolic links and Windows reparse points are rejected even when their target hashes match. Temporary Git repositories and synthetic binaries exercise this exact packaging entry, ZIP/hash/license read-back, and those negative cases; this evidence does not replace a real cloud product candidate or Windows 11 acceptance.

The candidate branch includes a production public trust bundle under `config/update-trust`, verified both by Python and the compiled client verifier. The protected-main workflow must still fail before reading API credentials if that reviewed bundle is absent from its own fixed checkout. Test fixtures and private keys are never accepted there. Candidate existence on a draft branch does not mean protected-main product construction has completed.

The Windows recipe pins `releaseDebugInformation: None`; the build record and the candidate ZIP's internal and external manifests carry the same policy. The release gate rejects a missing or mismatched policy whenever the reviewed recipe specifies it. This keeps PR and product Release builds consistent; the native compiler/linker probe verifies the actual flags, while the full cloud run must independently establish resource usage and completion.

## Signing preparation

Signing also reads `config/update-trust/root-public.pem` from the candidate's immutable parent commit and requires it to match the current reviewed root before issuer secrets are consumed. A later QA commit may renew issuer metadata under that root; changing the root requires a new candidate build and fresh QA.

The committed QA input uses schema 2 with only `schema`, `kind`, `approvedAt`, `candidate` and `checks`. Identity, machine descriptions and free-form notes are rejected; schema 1 is rejected rather than silently accepting private fields. Keep raw QA evidence in local private storage. Reviewed commits and protected-environment approvals establish human authorization, while this anonymous input binds all required passing conclusions to the exact candidate. Signing authorization and signing records no longer include an approver username.

After testing the exact downloaded artifact on local Windows 11 and verifying its cloud conclusion, program hashes, source archive and absence of account data, generate the QA template from `candidate/candidate-record.json` and commit an internal `fishgram-signing-qa` request under `release/qa/`. Keep incomplete search and installation checks false. The request timestamp records this review; authorization to access the issuer secrets is the separate protected release-environment approval. Complete installation/recovery and the remaining search acceptance using the signed package, then complete the same QA file under the full or explicitly approved Beta policy before publication. The external `candidate-record.json` is the sole signing record: it binds the candidate ZIP and corresponding-source ZIP (`name`, `size`, and SHA256), program hashes, parent/source/recursive pins, and reviewed tools. Do not submit the package's embedded `build-manifest.json` as the signing record; it cannot authorize signing by itself. The four internal-signing checks and the exact `sourceArchive` binding are mandatory before signing; publication additionally requires the completed acceptance policy.

Dispatch `sign-release-candidate.yml` from protected `main`, supplying the successful candidate run ID and QA basename. Before candidate artifact download, the workflow queries GitHub API and requires the same repository, `.github/workflows/product-candidate.yml`, `workflow_dispatch`, successful conclusion, `main` branch, matching head SHA, successful `candidate`/`candidateapproved` job, and uniquely run-owned artifact. It then verifies external candidate record, candidate ZIP, bound source ZIP and its Git blob contents, QA, reviewed pins, and Packer hash before exposing issuer secrets. No build or recompilation occurs.

The configured protected `release` environment supplies the encrypted PKCS#8 issuer PEM and passphrase as step-scoped secrets; `ISSUER_KEY_ID` is a public environment variable. If production trust files or this issuer ID are absent, signing stops; a maintainer must install the reviewed public trust bundle and environment variable through protected repository configuration. Test trust is never a fallback. Python consumes and removes both secret environment entries only after the independent preflight and Packer signing-input checks, applies a temporary restrictive ACL, and removes the encrypted key file after signing. OpenSSL receives the password through stdin (`-passin stdin`) and the signing payload through a temporary public-data file; neither is passed on the command line. The tool matches the decrypted key's actual Ed25519 public key to the reviewed production issuer PEM and root-signed manifest, checks expiry/revocation/channel groups, and rejects a single issuer when any required AND group cannot be met. Packer embeds the detached signature. Python parses the result, confirms payload and unsigned fields are unchanged, verifies the Ed25519 signature and root-signed trust manifest, then writes only the signed package and a public signing record. No root private key is used.

Local signing uses the same gate and Packer flow with `--private-key` pointing to an encrypted issuer PKCS#8 PEM; its password is read with `getpass`. The command never accepts a passphrase argument or a plaintext private key. A public signing record and successful local signature do not publish a GitHub release, tag, attachment, index, or trust key.

After signing, download that same package for local Windows 11 installation, restart and recovery acceptance. Public release requires the completed QA policy, verified signed package and recovery results; the publishing workflow then verifies public downloads before updating the selected index.

`key-maintenance.yml` checks committed issuer metadata daily and creates a deduplicated maintenance issue when expiry is within 45 days. It requires the reviewed production public trust bundle on default main and the repository variable `UPDATE_TRUST_MAINTENANCE_ENABLED=true`. Production trust is prepared on the candidate branch; the daily check remains disabled until it is merged to main. A local public-key verification on 2026-10-11 found no issuer expiry within 45 days. Issue writes use the repository-scoped workflow token. Recovery tools and the native cross-baseline snapshot hook have local synthetic tests; real account recovery and first-public-release acceptance remain incomplete. The separate [publishing workflow](PUBLISHING.md) consumes these reviewed signed artifacts and verifies public downloads before promoting the channel index.
