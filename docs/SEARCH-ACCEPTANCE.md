# 搜索实测与证据记录

本清单执行原 `restricted-global-search` 的八项验收，不修改其规格、性能目标或 Comet 状态。当前 helper、同一生产核心的模拟 transport/clock 测试与完整产品 UI 是不同证据层；逐项由独立 Verifier 判断，未执行、失败或跳过不计通过。

2026-10-13 用户决定暂缓性能优化，先推进其余工作。A7 的约 2 秒目标及已有真实测量保留，暂缓不计为验收通过。2026-10-19 用户批准首版 Beta 公开搜索性能及原生遗漏消息/媒体对照样本两项限制，保留待验；其余搜索和签名更新恢复验收须完成，稳定版仍要求完整验收。具体范围见 [Beta 发行](BETA-RELEASE.md)。

## 准备

记录候选父提交、源码提交、程序 SHA256、显示版本、Windows 版本及对应云端 run。只使用同一个固定候选，测试期间不重新编译或替换程序。真实账号使用独立工作目录，正常退出后的数据快照与异常退出保全副本分开记录；不把真实账户数据映射进 Sandbox。

选择匿名样本编号，私有记录保存对应消息和查询。至少准备原生全局搜索遗漏而会话内搜索可找到的受限消息、相应媒体及一个不属于当前范围的对照会话。缺少任何样本时记录缺项，不用无关命中替代。截图、查询词、消息正文、账号与频道名称留在私有区。

## 耗时与脱敏记录

生产日志 `RestrictedSearch: prepared` 记录来源数、Partial 和准备耗时；`RestrictedSearch: page` 记录已加载数、has_more、错误类型和从该轮 Coordinator start 开始的耗时。第一条 page 可作为协调器首屏耗时，不能直接当成从最后按键到 UI 绘制完成的耗时；后者另行实测。多页日志不能误当成多轮首屏样本。

公开报告只保留样本编号、版本/提交/哈希、范围类型、通过/失败/未执行、数量、耗时和已知限制。公开前逐项审查，不上传完整客户端日志；即使搜索统计行不含正文，日志其余部分也可能包含私人信息。

真实客户端未就绪时，准备样本和执行步骤即可，不填造成功。验收状态只能由 Comet Runtime 更新，本清单本身不是验收报告或发行批准。

## 当前规模测量的限制

2026-10-13 对源码 `de3752a42f60b59ae2af37ecdb749496b8e76a67` 的生产 Coordinator 重跑虚拟时钟测量，15 个规模/延迟组合均完整处理来源、未截断，并发补查最高为 6。RPC 模拟延迟为 100ms 时，6、10、20、106 个来源首屏分别为 1950、3150、6150、31950ms；这些时间从 Coordinator start 计，不能当成真实网络或 UI 绘制时间。

当前账号调度每次补查派发至少间隔 300ms，完整排序须等待各相关来源准备好或耗尽。106 个快速来源的派发下限约为 `350 + 105 × 300 + 100 = 31950ms`。1000ms/2000ms 模拟 RPC 下最高并发分别为 4/6，因此低延迟测量中的并发 1 不表示调度器只能串行。

这项证据说明大范围首屏有节流瓶颈，不证明 A7 通过。既有真实 FloodWait 说明移除节流也须验证服务行为；不能通过隐藏候选或提前提交不完整排序来替代原验收。约 2 秒目标保持不变，真实正常网络测量和最终判断仍待完成。

## 当前真实首屏观察

同一程序在正常登录的测试账号执行一次主搜索，界面先显示 `Loading...`，首屏返回后显示 `Loaded 50 messages`。生产统计记录候选来源 99 个、准备阶段 443ms、首屏 50 条、仍有后续页、协调器首屏耗时 39592ms。期间两个来源分别收到 3000ms FloodWait；最终 page 的 error=0 不代表本轮从未发生 FloodWait。

该时间从 Coordinator start 到首屏回调计算，不等于最后按键到界面绘制完成的时间。存在服务端限流，因此本次不能作为正常网络约 2 秒目标的通过样本；真实性能缺口仍保留。这次观察只验证一个主搜索样本的加载提示和已加载数量，不证明全部失败状态、媒体展示、重试或精确总数条件。

随后点击该主搜索样本的首条结果，实际进入对应频道并定位到与搜索摘要一致的原消息。这项证据只覆盖单条主搜索结果定位，尚未覆盖所有媒体和开启/关闭对照。当前源码的生产 Coordinator 集成测试已重新编译运行，13 组场景全部通过、无跳过；确定性场景仍与真实 GUI 结论分开。

搜索自身的 `Private chats` 类型筛选实测：切换后清除旧的全范围结果并显示加载状态，最终显示 `2 messages found` 和 `Private chats`，两条可见结果均为该类型。对应统计来源 5 个、准备 5ms、首屏 1315ms、loaded=2、has_more=0、error=0，本轮没有新增 FloodWait。这是一个小范围正常条件样本，时间仍从 Coordinator start 计算，不能扩大为全部范围正确或大范围性能通过。侧栏自定义文件夹与搜索范围分开：只切换自定义文件夹后，主搜索仍标为 `All chats`，不能用侧栏选中状态证明搜索范围受限。

取消再输入会重置为全类型搜索，实测来源恢复为 99 个，重新返回 50 条，未复用私人会话的两条结果。这一轮首屏 39410ms，仍出现两次 3000ms FloodWait。实际向下滚动触发第二页后，统计 loaded=100、has_more=1、error=0；回到顶部显示 `Loaded 100 messages`，原首条结果仍在。可见日期向旧推进，但目视不能证明全量标识去重与完整排序。续页 elapsed 从整轮开始累计，包含测试暂停时间，不能用作第二页 RPC 延迟。

## 空文本媒体切换观察

同一源码和程序哈希的独立测试客户端，从空搜索框选择 Photos，实际返回并显示 `Loaded 200 messages`。生产统计来源 99 个、准备 412ms、首屏 loaded=100、has_more=1、error=0、elapsed=36955ms，随后预取使 loaded 增至 200；该轮统计没有 FloodWait。再切换 Videos，旧内容清空，随后重新显示 `Loaded 200 messages`。新一轮来源 99 个、准备 2ms、首屏 34946ms，两来源各出现 3000ms FloodWait，预取后 loaded=200、has_more=1、error=0。

这证明空文本媒体过滤实际启动，以及这次类型切换重新执行搜索并展示加载数量；没有点击或播放媒体，尚不能证明所有返回项类型、原消息定位、开启/关闭遗漏样本对照或全部生命周期条件。Photos 的无 FloodWait 样本仍明显超出约 2 秒目标，不能计为性能通过。以上首屏时间来自协调器统计，不是最后按键到 UI 绘制的测量。
